# Model licence policy

This application downloads language models at runtime. That makes model licensing
a first-class engineering concern, not a footnote: a model that is fine to use is
not automatically fine to ship, and the difference is not visible in the code.

This document records **which models this project accepts, which it refuses, and
why**. Read it before adding a model to the catalogue.

## The four rules

**Rule 1 — the licence must be Apache-2.0, MIT, or BSD.**

Nothing else goes in the catalogue without this file being updated first.

**Rule 2 — the model must be downloadable without authenticating.**

A gated model cannot be fetched by the app, which forces an OAuth flow onto every
user. That is a real cost, and it disappears entirely if you only publish models
that need no credentials.

**Rule 3 — the first model in the catalogue must hold a Chinese conversation.**

This app has one audience and its interface is in Chinese. A model that has never
seen Chinese does not fail loudly: it answers a Chinese question with confident
English about something else, and the person reading it concludes the app is
broken rather than that they chose the wrong model for the job.

That is not hypothetical. An earlier build put an English-only 360M model —
the smallest, so the most tempting — at the top of the list, and "你可以干什么"
came back as a Python function for summing a list of numbers.
`ModelCatalogue.validate()` now refuses a catalogue whose first entry cannot do
Chinese, and every entry records what it can be talked to in.

**Rule 4 — the model must come from a Chinese lab, and be reachable from China.**

Two halves of one rule, and both about the audience rather than about engineering
taste. A model published elsewhere may not hold a Chinese conversation, its host
may be unreachable from mainland China, and its publisher has no stake in whether
it works there. `validate()` refuses a catalogue whose first source is
`huggingface.co`, because a model that cannot be downloaded in China is not a
model this app can offer.

Together, the rules mean: **the first model is eligible only if it is published
by a Chinese lab, declared Apache-2.0 or MIT, needs no credentials, and works in
Chinese.**

## Why Gemma 3 is refused

This is the one that catches people, because Gemma 3 is a good model and it sits
in the same Hugging Face namespace as the models we do accept.

Gemma 3 ships under the custom *Gemma Terms of Use*, not an OSI-approved licence.
Reported characteristics of those terms (The Elec, 2026-04-06, covering Google's
move to Apache-2.0 for Gemma 4):

- Google **could amend the terms at any time**, and continued use was treated as
  acceptance of the amended terms.
- Google retained the ability to **restrict usage remotely** — the report notes
  the concern that already-deployed products could be disabled.
- The restrictions **propagated downstream**: products built on the model, and
  models trained on synthetic data generated by it, carried the same limits.

For a project that is meant to be permanently open and permanently usable offline,
a licence that its own author can change unilaterally is disqualifying. The model
being technically excellent does not change that.

**Gemma 4 is a different situation.** Google moved it to Apache-2.0 and removed
the custom clauses, the redistribution limits and the inheritance of restrictions
into derivative works. Gemma 4 is therefore accepted — see the table above.

Do not generalise from "Gemma" as a family name. Gemma 3 and Gemma 4 do not share
a licence.

## The gated-model problem

`litert-community/Gemma3-1B-IT` is `GATED(auto)` on Hugging Face. Downloads are
refused unless the user has accepted the terms on the website and supplied a token.

That is why Google's own AI Edge Gallery asks every developer to register a
Hugging Face OAuth application before it will build: it needs to handle gated
models. Not shipping gated models means not needing OAuth at all.

If a future model requires gating and you still want it, the cost is:

1. An OAuth application registered with Hugging Face.
2. `clientId` and `redirectUri` injected at build time.
3. A sign-in flow in the app.
4. Acceptance of the upstream terms, which are then binding on your users.

Six of the accepted models are small enough that this is not worth it.

## Adding a model

1. Open the model page on Hugging Face.
2. Read the `license` field **on the page for the repository you will actually
   download from**, not on the upstream base model.
3. Confirm the page is not gated.
4. If the licence is Apache-2.0, MIT, or BSD **and** the page is open, add it to
   the catalogue.
5. Otherwise, do not add it. If you believe it should be an exception, write the
   reasoning into this file first — with a source URL and a date — before the
   model goes into the catalogue.

## A trap worth knowing about

Derivative repositories can declare a licence that the upstream did not grant.
A converted model republished from `google/gemma-3-1b-it` may show
`license: apache-2.0` while the upstream is `license: gemma`.

**Always check the upstream base model, not just the repository you download
from.** The Hugging Face API exposes it as `cardData.base_model`:

```bash
curl -s https://huggingface.co/api/models/<repo> | jq '.cardData.license, .cardData.base_model'
```

Repackaging does not create rights that the original publisher did not grant.

## Not bundled

No model weights ship inside the APK. The app downloads them from Hugging Face on
the user's behalf. This is deliberate:

- The user obtains the model from its publisher, under the publisher's terms.
- This project is not a redistributor of model weights.
- The APK stays small, and there is no stale copy of a model to maintain.

Keep it that way. Putting weights in `assets/` would change this project's legal
position and is not a packaging convenience worth having.
