# Roadmap

Every feature this project has decided to build, decided against, or has not yet
decided about. One row per item, with the state and where the reasoning lives.

**Why this file exists.** The list started as an answer in a conversation, and a
conversation is not a record — it gets summarised, and summarising is lossy. By the
time someone asked "how many are left", the numbered items past the first dozen
could no longer be reconstructed with confidence. A plan that spans weeks has to
live somewhere that does not forget.

**The rule for adding a row.** Every item cites what it is grounded in. An item
with no source is an opinion, and this project has a rule against building those:
search first, then build.

States: **done** · **done, half of it** · **next** · **todo** · **rejected** (with
the constraint that rejects it) · **blocked** (with what it waits on) · **not
started** (nothing is in the way, and nobody has begun)

| `lint` clean: 28 warnings to none | done | Run as one pass, because most of the count was one cause. **Fifteen** were the launcher icons: five legacy PNG pairs, deleted. The app has had a complete adaptive icon — background, foreground, monochrome — since it was generated, and `minSdk` is 26, so on every device the app can run on the PNGs were already being shadowed by `mipmap-anydpi-v26/`. They were dead weight that happened to be reported as four separate problems (`IconLauncherShape` for the square-versus-round shape, twice over, and `IconDuplicates` for the round file being a byte-identical copy of the square one). The folder then moved to `mipmap-anydpi/`, since `-v26` selects the same devices `minSdk` already admits — `ObsoleteSdkInt`. **Five** were `ModifierParameter`, and the earlier decision not to touch them was wrong for a reason worth recording: the objection was "five signatures, twenty call sites, style only", and the call-site half of that was never true — every one of the fifteen is a named-argument call, so moving the parameter is a change to one line per function. Three were dependency versions, one was a literal version in `build.gradle.kts` that belonged in the catalog, one was `Uri.parse` that has a Kotlin extension on a dependency already present, and one was `mutableStateOf` holding a `Long`. `targetSdk` went 36 → 37 to match `compileSdk`, which lint reads as a compatibility mode. `InlinedApi` is the one item suppressed rather than fixed, with the reason at the call: the constant is API 28, the branch is the 26-and-27 path, and the method is already wrapped so a device that rejects the flag gets UNKNOWN rather than a wrong verdict. |
| A stuck runtime no longer loads a second model | done | `awaitGeneratorThen` bounds the wait for a running generation to release the conversation, and on timeout deliberately does not close the handles — releasing them under a live generation is a native use-after-free. That part was right. What was wrong is what the caller did next: it returned `Unit` with a comment saying "the state says so", and nothing set any state. `load` fell straight through and built a second `Engine` while the first was still resident, and `releaseLocked` is the only thing in the class that ever calls `engine.close()` — so the second load leaked the first outright. Two multi-gigabyte models at once is a device crash, which is what the LiteRT-LM guidance says happens when a model is loaded twice. It now returns a `Boolean`, and `load` refuses with a sentence that names the cause and says the current model still works, instead of dying. `unload` ignores the result on purpose, with the reason written down: it returns `Unit` and neither of its callers can offer a next step. `resetConversation` was already safe. Found by a subagent audit whose finding was marked "not verified" and left alone for two rounds — the verification was reading the KDoc against the branch body and noticing that the branch body was a comment. |

Measured by `ThinkingBudgetTest` (`app/src/androidTest/java/com/kayoyak/demoapp/inference/ThinkingBudgetTest.kt`), `emulator-5554`, 2026-10-16, on the app's own 344,671,744-byte file, twice: `thinkingTokenBudget = 32` holds the trace to 48-53 characters where the same first question unbounded held 951; a budget of 128 leaves 210 characters and runs into the 256-token cap (65.4 s against 40.9 s); and on four questions with checkable answers the two settings answered **3 of 4 the same way** -- `off` in 31.1 s and 33.2 s across two runs, `budget 32` in 58.2 s and 58.4 s, with a visible trace on every question. The one they both got wrong is the only hard one (30 - (18 + 12 - 5) = 5) and they got it wrong differently (`x = 30 - 18 - 12 + 5 = 1` against `30 - 5 = 25`), so the budget changed the reasoning path without changing the outcome on this model. The setting therefore stays off; what changed is that it is a reading rather than a symptom, and a phone, a larger shipped model or a harder battery is what would reopen it. The test prints answers and timings and asserts nothing about quality -- its first version had an automated column that said 4 of 4 for an arm that had 3 of 4, because the wrong answer contains the digit it was checking for while restating the question, which is why the answers are the evidence. |

## How this file stays true

A feature is **done** when its tests pass, the gates pass, and the reasoning it was
built on is written down somewhere in `docs/`. An item is moved to **rejected** with
its constraint quoted, not just deleted. An item found to be unnecessary says so.

When a row changes, the reason goes in the same change. A roadmap edited to match
what happened is a record; one edited to look good is not.

**What "nothing left" means, and what it does not.** Three kinds of work can be
left, and only two of them are in this file. A row in **not started** or **blocked**
is recorded: this file names what it waits for, and that is answerable by reading.
Work no row records can still exist — a defect nothing has run against yet, a
question nobody has asked — and no reading of this file will show it. So a claim
that there is nothing left is a claim about the rows: every recorded item is either
done or waits on something named here. Anything stronger is a promise about the
unknown, and this project has already broken that promise twice in one afternoon
(2026-10-16): a "nothing left" was followed by a reading that found a channel the
engine never read, and the next one by a reading that found a pipeline no test had
ever driven end to end. Say which claim is being made.
